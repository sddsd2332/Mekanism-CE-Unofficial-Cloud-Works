# 实体数据特殊节点：范围供给式生物模拟评估

日期：2026-10-18。依据用户本轮提案、已修订的生物模拟 v2.0 设计及当前 CloudWorks 源码。此文仅评估，未实现新节点。

## 结论

可行。建议把“僵尸刷怪节点”定义为**实体数据供给源**：保存实体／档案引用、授权与覆盖范围；对应机器在范围内获得读取该实体掉落定义的资格，并自行承担时间、能量、输入和输出结算。

源节点本身不生产掉落，不向机器推送免费物品，也不需要在云端生成真实实体。

这个方案能把动态部分集中到带版本的 Runtime 数据快照，减少对全局配方重注册的依赖；但“接入数据”与“让加工机器执行这份数据”仍需新增通用 API，不能只给时间上下文增加一个字段就完成。

## 数据流

```text
实体特殊节点的配置／授权
  → 收集实际引用的数据键
  → 主线程边界采集原生表／受控提供者／学习库
  → 不可变、带版本的 MobLootDefinition 快照缓存
  → 冻结阶段计算区域命中、机器资格与目标选择
  → 编译到对应机器的节点执行计划和资源 ID
  → worker 消耗时间／能量并结算产出
```

可以参考现有时间边界：`CloudworksServerTickService.tickLoadedClouds()` 在主线程取得世界时间，再交给 Runtime。现有 RuntimeService 还会在派发前准备 `preFrozenGeneration`，这比直接改 clock context 更接近本方案所需的“原生边界采集 → 纯数据执行”模式。

## 传入多少数据

- 按实际需求的数据键采集，不扫描全部生物注册表。
- 建议键为 `实体 ID + 上下文档案 + 数据版本`，必要时细分变种。
- 例如 10 个僵尸节点和 2 个骷髅节点，在档案相同的情况下只需两份定义；12 个节点分别保存范围、启停和授权。
- 发布后的定义可共享；是否有资格使用由各 owner／团队独立校验。
- 结构编辑时增删需求引用，避免每个 tick 解码所有产线来重新统计。

时间是每 tick 更新的轻量标量。掉落定义只在首次需要、数据变更或显式刷新时重新采集；普通 tick 传版本或复用引用，不能每 tick 为每个节点加载表、创建实体或真实 roll。

如果产品要求的是“主线程持续真实模拟击杀并把结果送入云端”，那属于另一条有预算、排队和结果消费语义的执行管线，不能按传时间的成本估算。

## 节点与机器的职责

| 对象 | 负责 |
| --- | --- |
| 实体源节点 | 实体／档案引用、放置授权、范围、启停、当前数据版本及准备状态 |
| 世界数据服务 | 原生采集、缓存、不可变快照发布、刷新、停服清理和失败回退 |
| 范围绑定器 | 找到合格机器、候选实体源、明确目标和对应数据键 |
| 生物模拟机器 | 执行参数、升级、输入消耗、输出空间、随机数字结算及在途承诺 |
| worker | 只读冻结后的数值与索引，不查询 LootTableManager／World／Entity 或执行兼容回调 |

可以使用一个参数化原型，例如 `mobsim:entity_source`，其配置决定显示为“僵尸刷怪节点”或“骷髅刷怪节点”。不需要为每个实体复制 Java 类和解释器。

激活卡可改为授权放置／绑定指定实体源；放置、启用和蓝图导入均由服务端验证资格。蓝图只保存需求引用，不能凭空复制激活权限。

## 范围与重叠的建议

- 仅影响同一产线中明确声明接受实体数据的机器。
- 范围和超过半面积判定可复用现有 `CloudworksAreaGeometry`；首版可以沿用下界源的 780×780 与严格大于 50%，但应作为实体源自身的参数声明。
- 同实体、同档案的多个源不重复增加掉落或吞吐。
- 一台通用模拟机若只命中一种实体，可自动选中；命中不同实体时由玩家选择目标，或显示“等待选择实体”。
- 选定僵尸的机器只读取僵尸定义，不因范围内另有骷髅源就同时获得骷髅掉落。
- 不建议以节点遍历顺序、最后放置顺序或未声明的“最近源”决定结果。
- 同实体档案可以合并覆盖显示；不同实体的范围应保留区分，避免并成一个无法辨认数据来源的大框。
- 停源、移出范围或数据不可用时停止发起新工作；已经付款的在途操作保留原输出承诺。

## 需要新增的 API 与实际缺口

以下名称仅是能力建议，不是已存在接口：

1. **带版本的 Runtime 数据提供者 API**  
   注册提供者和键类型，按需求准备不可变快照；发布时携带世界会话与数据版本，支持刷新失败保留旧版。

2. **范围数据源行为 API**  
   特殊原型声明供给的数据类型、目标接受契约和范围策略。现有 `CloudworksSpecialNodeType` 只有方向、端口、资源选择要求和配置校验，注册 SOURCE 并不会自动获得新的执行解释器。

3. **按节点编译执行计划的 API**  
   在原生边界把机器＋选中数据源＋机制档案编译为回调已执行完毕的 RecipeSpec／等价数值计划，worker 只消费结果。

4. **数据版本与提交有效性**  
   依赖数据更新必须触发受影响节点重编译，且纳入结果有效性检查。在途承诺继续兑现旧契约，新操作才切换新版本。

特别注意现有 `CloudworksRuntimeCatalog` 主要按机器能力 key 共享加工配方。两台同型号机器分别绑定僵尸与骷髅时，执行缓存必须再区分实体档案和版本，不能误用同一份配方表。相同实体档案和机器机制则可以继续共享编译结果。

这条扩展路线可以保持机器和端口的加载期声明不变，另建受控数据快照入口，而不必每次观测都增加 RecipeHandler 全局版本并重新开放全部 adapter 回调。

## 仍然需要解决的掉落问题

特殊节点改变的是数据供应与选择方式，不能自动解决数据本身的保真度：

- 仍需共用 MobLootDefinition、原生与观测数据来源标记。
- 首批可用已有独立概率输出；若要求加权互斥多产物组的联合分布一致，仍需对应数值契约。
- 双源差分、删减／替换、净化重掷白名单、激活权限与 NBT 规范化仍按 v2.0 评审边界处理。
- 没有数据时显示“准备实体数据／数据不可用”，不能回退到任意实体的掉落。
- 学习新物品必须先在边界注册其资源描述符，再交给 worker 的纯数字计划。

## 推荐实施顺序

1. 一个参数化实体源＋一种生物模拟机器＋固定僵尸定义，打通授权、范围命中、耗时耗能和输出结算。
2. 增加骷髅源，验证同型号机器绑定不同源的隔离、同类不叠加、多类型重叠选择。
3. 接入版本化主线程数据采集和按节点执行计划发布，先支持启动／管理员显式刷新。
4. 接通上游配方 IR 与学习库；最后增加复杂分布和观测兼容。

这是“范围数据供给平台＋生物模拟内容”的一批功能，现有范围 API、渲染、授权保存和结算可以复用；主要工程量在数据发布、按节点执行缓存及生命周期，而不是节点图标。

- `CloudworksServerTickService.java:170`：世界时间主线程边界。
- `CloudworksRuntimeService.java:162–210`：owner 快照、原生生成计划准备、worker 内编译。
- `CloudworksRuntimeCatalog.java:67–109`：当前加工配方的共享 key 与冻结入口。
- `CloudworksAsyncRecipeAdmission.java:17–52`：现有加载期 adapter 冻结限制。
- `CloudworksNodeEnvironment.java`、`CloudworksAreaGeometry.java`：已有范围源与目标筛选。
- `CloudworksSpecialNodeType.java`：现有特殊节点声明面。
