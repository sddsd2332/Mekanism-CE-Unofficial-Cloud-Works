# 生物模拟上云评估：以设计文档 v1.8 为准

日期：2026-10-18。评估对象为 `MOB_SIM_CLOUDWORKS_INTEGRATION_DESIGN_20261018.zh-CN.md` v1.8，已重读全部章节，尤其是 §8.5.6 的编译器和 §8.5.7 的双源差分。此文仅评估，不代表已实现生物模拟。

## 结论

推荐 v1.8 的融合态：**配方承载掉落定义，激活卡承载使用资格，观测提供带上下文的补充证据，云侧消费不可变数字契约。**

但不能按“云侧额外代码归零”估算。当前主要缺口是世界数据与运行期配方的刷新边界、激活卡匹配／授权，以及复杂掉落的数值表达。双源观测有价值，但不宜直接作为自动修改全服配方的权威来源。

前文 v1 保留的“云内没有随机”“/reload 会自动重跑云冻结”“FarmOutput 与 loot 表同构”等结论，应统一按当前代码和后文修正，避免实施时混用不同版本的假设。

## 1. 可以复用和不能直接复用的部分

| 能力 | 当前状态 | 接入建议 |
| --- | --- | --- |
| 数字概率产出 | 已有 `CloudworksRecipeSpec.chanceOutput`，Runtime 已执行随机结算 | 可直接表达独立概率项，不需要先造一套 RNG |
| 独占输出 | 已有均匀单品 `choiceOutput` | 不能直接替代任意权重、可含多个产物的互斥组 |
| 数量区间、加权互斥产物组 | 现有 RecipeSpec 不能完整表达 v1.7 的一般结构 | 首批明确采用均值投影；要求联合分布一致时再补通用组 API |
| 配置模板 | 已有 CONFIGURATION 端口及 `configuration` / `configurationMatcher` | 适合不消耗的激活卡；是否作为耗材需单独定价 |
| 模块与机制 | 已有物品绑定、接受策略、机制配方变体 | 可复用；不能把多个独立修饰模块都设为 REPLACE |
| 配方版本变更 | 现实机器可据版本重查；云适配器有额外冻结缓存 | 不能把两者当成同一条自动更新链 |
| 扩展存储 | 现有扩展容器主要随产线、草稿、蓝图流转，单项 16 KiB／合计 64 KiB | 存小型设置、引用和版本号，不存全服掉落学习数据库 |
| JEI／CT／GS | 有种植站等实现先例 | 需要新增配方处理器、展示与转换代码，不会由新输出类自动获得 |

Runtime 的随机是可复现的伪随机数字运算，符合零 World、零插件回调约束；这不等于每次固定产出均值。

## 2. 必须先修正的生命周期假设

### 云配方冻结早于世界可用

当前入口是 `Cloudworks.loadComplete → CloudworksBootstrap.loadComplete`。世界与存档在后续 `serverStarting` 才取得。`CloudworksAsyncRecipeAdmission.freezeRegisteredAdapters()` 完成后，`capture()` 不会任意重新调用 adapter。

本地 1.12.2 的 `LootTableManager(File)` 构造器本身就调用 `reloadLootTables()`，不能沿用“构造后等待首次 reload、映射为空”的时序假设。

因此：

- 不能在现有 load-complete adapter 中依赖 `overworld.getLootTableManager()`。
- `FMLServerStarted` 可以作为世界数据首次采集点，但目前不是“重新开放机器／配方注册”的钩子。
- `RecipeHandler.getGlobalRecipeVersion()` 改变会使旧冻结视图过期；`complete` 已关闭时并不会自动重编译。不能据此承诺云机器下 tick 自动获得学习配方。
- 不应把测试用 reset 方法用于生产 reload，也不能为单个学习项反复重启整个注册生命周期。

### 建议补世界级配方快照发布 API

下面是待实现的能力描述，不是现有 API：

```text
模组加载期：
  注册机器身份、端口、执行族、数据提供者声明

ServerStarted / 显式数据刷新：
  主线程边界加载目标表与模组数据
  → 转成不持有 World/Entity/LootTable/回调的不可变 MobLootDefinition
  → 编译并校验候选配方目录
  → 在受控边界原子发布 providerRevision
  → 刷新该提供者的配方、机制派生缓存、符号和 Runtime 目录
```

全量候选失败时保留旧版本；在途操作兑现原有输入扣款和输出承诺，新操作才采用新规则。发布需明确安全可见性与 worker 边界，不能只依赖“生命周期代码按顺序执行”。

第一批可以先只在启动和管理员显式刷新时更新，不实现每次观测后立即热注册。若不补发布 API，就只能采用模组加载前已有的预生成数据并接受重启后生效。

### World 边界的正确表达

禁止的是 World／Entity／LootContext／任意原生回调进入 Runtime，不是服务端采集边界永远不能读取 World。现有 Cloudworks 启动代码本身就读取世界保存目录。

`LootTableManager` 是可懒加载、可 reload 的活服务，不能因为字段里没有 World 就当成不可变快照交给 worker。读取或展开之后应立即生成脱离原对象的 DTO，并在停服／换世界时清理会话状态。

## 3. v1.8 双源差分需要收口的规则

### 必须区分三份结果

同一次死亡至少分开保存：

1. **实际表结果**：真正用于这次掉落的原表输出。
2. **受控基线样本**：如果获准额外采样，使用独立上下文和 RNG 的结果。
3. **事件列表快照**：观测时刻 `LivingDropsEvent` 中的物品。

差分只能用第 3 项减第 1 项。不能拿事件结果减额外重掷结果，否则两次随机不同就会产生虚假的“表外掉落”。

物品先按注册 ID、metadata、完整 NBT 合并数量，并在边界立刻复制，避免后续修改影响前一次观测。

### 差分不一定是追加

模组可能减少、取消、替换、变更 NBT 或增加产物。`finalOut - tableOut` 可以出现负数。

例如表掉 1 个生肉，事件将其换成 1 个熟肉，差分应为 `生肉 -1、熟肉 +1`。只把熟肉追加到原配方会双倍产出。

应记录有符号残差及上下文。第一批只把经过审核、证明确为正向追加的规则转成额外产物；删除／替换保留为观测证据或单独的覆盖规则。两个层独立 roll 也不自动保留原先的相关性。

### 关联标识与递归去重

- 不只使用 entityId＋tick：至少包括服务器世界会话、实体 UUID、死亡序号。
- 包装层记录顶层死亡表结果；嵌套表已包含在父表结果中，不能再次相加。
- 为采样重入设置作用域标记，用 try/finally 清理；额外采样不能再次触发学习或增加击杀数。
- 每次死亡只计一次样本，零掉落也要计入分母，取消事件单独处理。
- 击杀激活计数与有效采样计数分开；`doMobLoot=false`、禁止掉落等情形不能当成正常零产出样本混入掉率估计。

### LivingDropsEvent 不是最终落地的保证

它是可取消、可继续被后续监听器修改的事件；LOWEST 也不保证没有同优先级后续修改。之后 `spawnEntity` 还可能失败或被取消。直接向世界生成物品、完全绕过父类死亡流程的模组也可能绕开此列表。

因此可承诺的口径应是“所选事件边界观测到的掉落”，不能写成自动覆盖一切最终落地物。

### 装备过滤

“按耐久物品特征剔除”会误删真正的武器／盔甲战利品，也不能识别所有装备来源。要精确排除装备，应在 dropEquipment 阶段取得来源；否则将其作为近似过滤选项并明确误差，不能宣称精确区分。

## 4. 净化重掷与表包装的风险

- 模组自定义 loot entry／function 可以访问世界、修改实体、发事件或进行昂贵计算，额外 roll 不保证纯函数或微秒级耗时。
- luck=0、player=null 不等于清除了所有上下文；DamageSource、燃烧状态、实体变种、难度、维度及模组抢夺事件仍可能影响结果。
- 默认只对明确支持、可确认安全的提供者采样；未知实现只做被动分层观测。额外采样使用独立 RNG、预算和重入保护，不复用实际掉落的 RNG。
- 替换成空池的 `ObservedLootTable` 后若只覆写 `generateLootForPools`，继承的 `freeze/getPool/addPool/removePool` 操作的是包装层池；Gson 序列化也读取其池。必须完整委托或提供统一 unwrap 路径，否则可能破坏冻结、展开器和其他修改器。
- 世界目录自定义表跳过 LootTableLoadEvent 是源码明确行为，新版接受此边界可以；将来需要覆盖它们，应另加采集钩子。

首批建议被动采集实际上下文、保留数据来源，暂不默认执行未知模组的“净化重掷”。

## 5. 编译器与唯一权威 IR

认可 `MobLootOutput` 表达独立项和互斥组的方向，但它应消费共同的不可变 `MobLootDefinition`，而不是让现实机器与云适配器分别重新解释原始表。

建议 IR 至少包含：

- 实体／表／上下文档案 ID，数据来源、规则版本、内容 hash。
- 独立项、带权互斥组、抽取次数、数量分布、空选项、条件与适用域。
- 物品完整描述符、已知／未知项、样本数与观测频次。
- 表基线与事件残差分层，是否允许自动用于生产。

编译器的必要规则：

- 1.12 原生 entry 是 item、loot_table、empty，加 Forge 扩展；Group／Sequence 不是该版本原生类型。
- 使用递归栈阻断环，并用缓存复用已编译子表；不能用一个全局 visited 集把合法的重复引用吞掉。
- 不能把未知函数忽略后直接发原始 item；SetNBT／metadata／damage 等会改变物品身份。
- 抢夺不只是统一倍率：`LootingEnchantBonus` 是随机增加、取整并可能封顶，另有概率条件随等级改变。若定义一个独立的“模拟机倍率升级”，应明确它是新规则，不声称等价原生抢夺。
- 同一张表不保证所有实体变种结果相同，实体属性条件仍可能分流。
- 全量超集、均值投影、精确随机应是明确的不同模式。前两者不能承诺保留原生联合分布。

## 6. 激活卡与配方输入

推荐卡只保存实体／档案引用、资格和审计信息，不保存全服学习数据库。

- 实体模板默认走 CONFIGURATION 端口，不消耗；确实要按次消耗时才使用 INPUT。
- `killed_by_player` 的原生条件看 LootContext 中的 player，而 EntityLiving 可以根据 recentlyHit 和 attackingPlayer 填入它；不等价于玩家必须造成致命一击。致命一击可以是产品规则，但应明确比原生条件更严格。
- 排除 FakePlayer；是否接受弹射物、宠物、间接击杀及交易卡需要明确规则。
- NBT 中写 UUID 和计数只能提供审计信息，不自动构成防伪。需要服务端权威登记或可验证凭证，且不能通过蓝图复制学习权限。
- 当前 matcher 对物品 NBT 是完整比较。激活者 UUID、击杀计数、卡序列号不同会令全局固定配方匹配失败。
- 应先决定激活卡是否规范化为固定的语义 NBT；若保留唯一审计字段，则补数据化 NBT 子集匹配与服务端资格校验，不能为每张卡注册一套配方。

## 7. Q1—Q11 答复

| 问题 | 建议 |
| --- | --- |
| Q1 桥接与生命周期 | 首次世界采集放 ServerStarted；先补世界级配方快照发布能力。manager 只留在会话采集层，停服清理，不进入 Runtime。 |
| Q2 AT 或反射 | 配方案不消除生成器所需访问。优先集中式只读 AT／Accessor；采用反射时统一封装并验证目标字段。清单还缺 LootTable.pools、poolConditions、SetCount 和抢夺参数等。 |
| Q3 小数产出 | 允许随机时直接用现有 chanceOutput；严格均值可用有界周期放大。要精确、细粒度且无随机，就补云端可持久化结算余量，不能放到现实侧累积器代管云执行。 |
| Q4 学习文件 | 存档下模组自己的版本化数据文件，原子保存；云扩展只存引用、版本和小型设置。WorldSavedData 也不是天然违规，关键是只在边界操作。 |
| Q5 抢夺／灼烧／精密 | 属于机制或执行档案，而非纯时间／能量曲线。当前多个 REPLACE 会冲突，首批用一个完整、互斥的组合档案，或先补可组合的变换管线。 |
| Q6 产出乘数 | 第一批不为此增加全局／通用产出乘数。按档案生成最终 outputs/chances，更容易保留取整、上限、容器返还和不可缩放项。 |
| Q7 附魔产物 | 不穷举全部组合；受控白名单与带上下文观测。观察一次不证明概率或最大数量，不能自动升级为无限量产规则。 |
| Q8 卡做 IR | 认可中间表示，但让不可变定义／配方目录承载 IR；物品卡只作引用和资格。脚本可以覆盖服务端定义。 |
| Q9 现实真表或卡 roll | 若选择配方案，建议现实模拟机和云端都消费同一 MobLootDefinition。真实死亡作为校准证据。需要拟真真表模式时单独标注其与数值模式的语义差异。 |
| Q10 激活细节 | 门槛参数化；交易与绑定是产品决策。记录零产出和上下文分母；“至少见一次的概率 95%”不等于“掉率估计有 95% 精度”，未知稀有项不能据此宣称完备。 |
| Q11 宿主定线 | 选融合态 C：配方为数据主线、卡为钥匙、被动观测为证据、云为快照消费者；删除“云集成归零、JEI 免费、自动下 tick 刷新”等过度承诺。 |

## 8. 推荐实施顺序

1. **IR 与固定配方闭环**：只做少量已知生物、基本数量和独立概率，明确云端采用哪种投影模式；补 MobSimRecipeAdapter 和激活模板规则。
2. **世界数据发布能力**：启动／显式刷新事务、版本缓存失效、在途承诺保留、失败回退。完成后再接自动生成器。
3. **激活与存储闭环**：击杀归因、服务端资格、交易、持久化与蓝图不携带权限。
4. **被动双源观测**：死亡关联、根表去重、带符号残差和上下文分层，先提供审核／诊断，不自动改生产配方。
5. **扩展保真能力**：确有需求再加加权多产物组、精确数量分布、受控净化采样及复杂附魔变体。

至少验证：互斥掉落不同时出现、嵌套表不重复计数、替换／删减事件、取消事件、无表与无事件路径、FakePlayer／宠物／间接击杀、未激活卡拒绝、不同审计 NBT、刷新失败回退、在途兑现、重启后 RNG/数据版本稳定和多个存档不串数据。
