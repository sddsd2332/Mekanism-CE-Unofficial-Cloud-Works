## 1. 冷捕获只解码一次与冷编译限流

Runtime service 在一次编译作用域内调用一次 `VirtualSnapshot.lines()`，将同一份私有解码结果传给资源预冻结、发电计划冻结、detached capture、catalog 和 ColdData。原公开 `lines()` 仍返回防御副本，没有全局缓存可变产线。

`CloudworksNativeContracts.prime` 不再重复解码整线，也不再从节点 NBT 重建已解码过的模块机器。发电计划直接使用已解码节点，仅对确实包含发电分支的节点计算环境。资源字典变化后的编译重试复用该捕获的解码结果。

同一 service 最多同时在途两个冷编译（工作线程只有一个时最多一个）；普通已编译 owner 的推进不受此上限限制。等待编译的 owner 继续累积逻辑时钟，不抹去欠账。本轮未将独立节点或产线的生产语义合并。

## 2. 候选缓存和等待规划失效

没有动态 candidate 回调的条件候选，在编译 epoch 内按节点复用，配方表或环境快照替换时失效，候选优先级和轮转规则不改。

无动态 pre/candidate/post 钩子、无复杂分支/随机/小数副燃料/时间环境条件的普通加工节点，在缺输入、缺模板、无匹配等等待状态下，保存输入/输出/配置库存版本和配方表身份。版本或状态变化后立即重新规划；单配方堵输出也可复用等待结果。预留和释放同样改变库存版本，因此它们会唤醒检查。

运行中的操作、能源等待、热系统、发电机、动态 addon 回调仍按原 tick 路径执行；没有实现黑箱、平均产量替代或跨 tick 资源结算。

## 3. 确定性配方的批量快路径

对原料集合互不重叠、没有重复匹配项、无随机/小数副耗料的固定配方，直接求输入数量上限；若上限通过原输出/能源约束，立即采用，否则保留二分约束搜索。独立输入的可行性检查不创建 Allocation，最终接纳时才构造真实分配结果。

重叠原料继续使用原精确流分配，随机/选择产出继续走原随机流，非整数倍率的安全门禁保持原样。没有动态 pre-work 的确定性配方省去重复的收敛搜索。确定性输出检查直接累加 codec 数量，不为搜索试探构造产出列表。

## 4. 在途产出汇总与检查点共享

`CloudworksRuntimePromises` 是每个 worker simulation 的单份临时汇总，按物理根节点和操作存储版本失效；同一批量搜索中的多次检查复用汇总。新建、替换产物、完成、取消、恢复等操作变更均使旧汇总失效。没有给每个节点永久分配整套 codec Map，整数溢出继续返回不适配。

版本检查点改为不可变的 256 项分页快照。未变化的机器、库存、配置、操作、热状态和通道版本页在新旧检查点间共享，变化页复制，旧检查点不被后续 worker 写入污染。原有脏节点判断、机器 NBT 增量投影与内存发布继续保留。

## 5. 持久化准备与有界已提交视图

后台 IO 在成功耐久提交后保留有界的只读 NBT 视图与指纹。预算是最多 128 项、文件字节总量 16 MiB，NBT 对象实际堆占用可能高于原始字节数；缓存位于队列 Sink 作用域，不是每个节点或每个在途事务一份。

Windows 上单靠大小/时间戳/文件标识不能可靠识别同属性替换，回归已经捕获该情况。因此命中复用前仍流式读取并校验文件 SHA-256，只有内容一致才复用已解析 NBT；本优化减少的是重复解析和对象分配，**不宣称零磁盘读取**。正常读写流顺便计算原始文件摘要，避免提交后额外重读。

严格恢复直接绕过视图缓存并清空批内旧视图；批次失败清空缓存，挂起意图和端口 journal 文件不缓存。file force、原子替换、schema、交易顺序及既有后台 journal 归并协议保持原样，没有引入新 WAL 格式。

同一意图的投影路径只建立一次；NBT patch 通过单次递归生成变化项，省去每层先做深 equals、再递归比较的重复扫描。补丁仍是原来的绝对字段/索引赋值，可重复重放。

显式 flush/正常停服按 owner 合并尚未物化的 Runtime 产线和仓库 delta，复用已冻结的产线投影，通过既有意图日志提交。主线程不再为了保存而重建全部节点；正常编辑仍在需要时物化最新投影。IO 侧原结构校验、逐文件 force 与原子替换继续执行。

## 服务端夹具修正与证据范围

初轮 `cw_phase2_20261026_a_*` 原始结果保留，但不能直接作为最终稳态对照。冷编译限流使旧的“等待 5 秒”不足以保证全部 owner 完成编译，r2 开始测量时仅约一半 owner 已编译，测量中还在冷编译和追赶历史 tick；27.55 tick/s 包含追赶，不能声称实时生产超过 20 tick/s。

夹具新增只读就绪诊断：全部 owner 完成冷编译后，再等待至少 5 秒无明显总欠账回落的窗口，并保留原 vanilla 追帧检查。饱和负载允许欠账增长，不以“所有欠账必须为零”阻止性能不足的负载进入测量。报告记录编译就绪、稳定窗口和初始欠账。

初轮 r3 在 200/300 测量 tick 后核账失败：`Unmodelled native output in thermalexpansion/14`。TE 凝结机以同一种水输入可合法选择雪、冰、浮冰，旧夹具只给单个选中配方记账。修正为读取真实冻结表的同输入、单确定性输出候选，为各合法产物分别配置收集和资源等价账，逐项用原生耗水/产出系数核对；未知产物、部分配方产物或无法唯一核算的耗料比例仍报错。不改生产配方，不合并概率条目，不制造配方，也不跳过 TE 机型。

最终复测使用新 runId `cw_phase2_20261026_b_*`。初轮结果和失败日志不覆盖。

最终源码回归日志：`build/qa/runtime-phase2-stable-regression.log`；默认发布构建日志：`build/qa/runtime-phase2-stable-release.log`。两者通过，正式 JAR 已核对不含 fullScaleStress/spark 类。IDE MCP 后续连接不可用，最终有效构建与回归以 Gradle 实际结果为准。
